# ARCHITECTURE-ru.md

# Архитектура проекта

Проект: gentk

Назначение документа: описание внутренней архитектуры, правил организации кода и ограничений.

---

# Цели архитектуры

Основные цели:

- предсказуемость;
- расширяемость;
- простота сопровождения;
- минимизация связности между модулями;
- высокая связность внутри модулей;
- отсутствие "god objects";
- минимизация дублирования.

Архитектура предпочитает явный код сложным абстракциям.

---

# Основные принципы

Проект следует:

- SOLID;
- SRP;
- KISS.

---

# Single Responsibility Principle

Каждый модуль должен иметь только одну причину для изменения.

Примеры:
- CLI-парсер отвечает только за разбор аргументов;
- конфигурация — за загрузку, merge и валидацию;
- генераторы — за генерацию значений;
- вывод — за отображение.

---

# Open/Closed Principle

Добавление новых генераторов (KSUID, XID, Hashids) выполняется добавлением нового файла команды в `src/commands/` и расширением CLI/фабрики, без изменения существующих команд.

---

# Interface Segregation Principle

Интерфейсы должны быть небольшими.

Предпочтительный контракт команды:

```rust
trait Command {
    fn execute(&self) -> Result<(), AppError>;
}
```

---

# Dependency Inversion Principle

Высокоуровневые компоненты не должны зависеть от деталей реализации. Команды работают с абстракциями.

---

# Слои приложения

Архитектура состоит из слоёв:

```text
CLI
 ↓
Command Factory
 ↓
Command
 ↓
Output
```

Генераторы встроены непосредственно в файлы команд (без отдельной папки `generators/`). Это упрощает структуру и уменьшает фрагментацию.

---

# CLI слой

Назначение:
- разбор аргументов;
- валидация типов;
- help-страницы;
- регистрация подкоманд.

Не должен генерировать значения или выполнять бизнес-логику.

Каталог: `src/cli`

Help-система построена на derive-макросах `clap` с атрибутами `help`, показывающими допустимые диапазоны (например, `--length <8-65535>`).

---

# Command слой

Назначение:
- выполнение сценария;
- инкапсуляция логики генерации для своей команды.

Не должен заниматься парсингом аргументов или сериализацией.

Каталог: `src/commands`

Каждая команда (password, uuid4, uuid5, …) — это один файл, содержащий и структуру команды, и логику генерации. Это сохраняет связность без введения отдельной директории `generators/`.

---

# Config слой

Назначение:
- значения по умолчанию;
- загрузка JSON;
- merge приоритетов;
- валидация.

Каталог: `src/config`

### Приоритет конфигурации

Все команды используют общий `gentk.json`.

Порядок поиска:

```text
встроенные значения
    ↓
./gentk.json
    ↓
$XDG_CONFIG_HOME/gentk/config.json (или ~/.config/gentk/config.json)
    ↓
%APPDATA%\gentk\config.json (Windows)
    ↓
/etc/gentk/config.json
    ↓
аргументы командной строки
```

CLI имеет наивысший приоритет.

Команда `config` генерирует полный JSON с конкретными значениями по умолчанию для `password`, `uuid5` и `nanoid`, и пустыми объектами для остальных секций.

---

# Output слой

Назначение:
- печать значений;
- уведомления (notice);
- запрос подтверждения.

Каталог: `src/output`

- `Printer` управляет форматом: обычный текст с пустыми строками вокруг значений или JSON `{"value":"…"}` / `{"values":["…"]}`.
- `Notice::warn` выводит предупреждения в stderr.
- `Notice::show` запрашивает подтверждение `[y/N]`.

---

# Error слой

Назначение: описание ошибок приложения.

Каталог: `src/errors`

Единый enum `AppError` (использует `thiserror`):

- `CliError`
- `ConfigError`
- `ValidationError`
- `GeneratorError`
- `IoError`
- `SerializationError`
- `NoticeAborted`

---

# Randomness слой

Назначение: криптографически стойкая случайность.

Каталог: `src/random`

Используется крейт `getrandom` для прямого доступа к случайности ОС. Реализован лёгкий `OsRng` с методами `gen_range` и `choose`. Крейт `rand` не используется.

---

---

# Ограничения на размер файлов

- Предпочтительно: 30–100 строк.
- Допустимо: 30–130 строк.
- Нежелательно: более 150 строк (следует разделять).

---

# Команды

Каждая команда реализует `trait Command` с методом `execute`.

---

# Factory

`CommandFactory` отвечает только за создание команд, объединяя настройки из конфигурации и CLI. Factory не выполняет команды.

---

# Генераторы

Логика генерации встроена в файл команды. Генераторы не выводят текст (только возвращают значения). Выводом управляет `Printer`.

---

# Поток данных

```text
CLI
 ↓
Типизированные аргументы (+ конфиг)
 ↓
Factory
 ↓
Command (с встроенным генератором)
 ↓
Output (Printer)
```

---

# Правила зависимостей

Разрешено:

```text
CLI → Command → Output
Command → Random
Command → Config (через фабрику)
```

Запрещено:
- Командам зависеть от CLI-деталей.
- Генераторам использовать `println!`.
- Генераторам самостоятельно загружать конфигурацию.

---

# Уведомления (notices)

`Notice::warn` — предупреждение без остановки выполнения.
`Notice::show` — запрос подтверждения `Continue? [y/N]`, ответ по умолчанию `No`.

---

# Help-система

Справка генерируется `clap` и показывает допустимые диапазоны.

- `gentk --help`
- `gentk password --help`
- `gentk uuid5 --help`
- …

---

# Версионирование (автоматическое)

- `build.rs` при `--release` вычисляет хеш `Cargo.lock`.
- При изменении зависимостей инкрементируется минорная версия, сбрасывается патч.
- Без изменений — инкремент патча.
- Debug-сборки читают последнюю версию из истории и добавляют `-dev` (переменная `GENTK_VERSION`).
- `--version` выводит версию.

---

# Будущие расширения

Добавление нового генератора:
1. Новый файл в `src/commands/`.
2. Новый вариант в `Commands` (cli/parser.rs).
3. Дополнение `CommandFactory::create`.

Существующие команды не изменяются. Планируется TCP-сервер.
